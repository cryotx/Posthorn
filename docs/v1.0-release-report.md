# Posthorn v1.0 — final release report

**Date:** 2026-09-08
**Branch:** `feat/multi-provider-gateway`
**Scope:** the v1.0 completion round. After this the architecture is frozen.

---

## 1. Architecture

**Frozen shape, as specified.** One Go binary, one SQLite file, one instance,
one writer. No Redis, Kafka, RabbitMQ, PostgreSQL, Elasticsearch, Kubernetes,
distributed locks, or microservice split — none were introduced, and the
places where one would have been the easy answer are recorded as decisions
instead (ADR-51, ADR-52, ADR-57).

- 25 Go packages plus `cmd/posthorn`; 26,071 lines of implementation and
  32,033 lines of tests.
- Four direct dependencies: `BurntSushi/toml`, `google/uuid`,
  `hashicorp/golang-lru/v2`, `modernc.org/sqlite`. Every provider client is
  bespoke (ADR-1).
- `transport.Router` implements `transport.Transport` (ADR-26), which is why
  four feature rounds have been added downstream of it without refactoring
  the routing core.
- The v1.0 round added five packages — `netguard`, `mask`, `queryapi`,
  `admin`, and the audit/override/backup surface inside `storage` — and
  changed no existing routing, quota, breaker or retry logic.

**Deliberate non-goals, not built:** SaaS billing, user registration, complex
RBAC, marketing campaigns, newsletters, template designers, visual builders,
horizontal scaling, multi-region, distributed transactions, exactly-once
provider delivery, AI writing assistance.

## 2. Providers

Two native adapters added this round, both written against the vendors'
**current published references fetched on 2026-09-08**, not from memory.

| provider   | send | webhook     | verification | remote quota |
|------------|------|-------------|--------------|--------------|
| brevo      | yes  | yes         | unsupported  | unsupported  |
| cloudflare | yes  | unsupported | unsupported  | unsupported  |
| mailgun    | yes  | no          | no           | no           |
| postmark   | yes  | yes         | unsupported  | unsupported  |
| resend     | yes  | yes         | yes          | unsupported  |
| ses        | yes  | no          | no           | no           |
| smtp       | yes  | unsupported | unsupported  | unsupported  |
| webhook    | yes  | unsupported | unsupported  | unsupported  |

Three values only, no ambiguity (ADR-47):

- **`yes`** — implemented and usable.
- **`no`** — the provider offers it; Posthorn has not implemented it. A gap
  that could be closed.
- **`unsupported`** — the **provider** does not offer it. Nothing to
  implement. Every `unsupported` carries a one-sentence reason in the
  registry.

The matrix is **enforced, not documented**: `cmd/posthorn/capability_test.go`
checks it against both the transport registry and the webhook adapter
registry. A row claiming a webhook with no adapter mounted, or a provider
accepting a `signing_secret` it cannot check, fails the build.

**Why these two earn native adapters** (ADR-48 — a native adapter must beat
the generic SMTP relay at something nameable):

- **Brevo** returns a reliable per-message id that its webhooks carry back.
  That join is what the attempt trail and the delivery projection are built
  on, and SMTP cannot provide it — the relay decides what to report at
  hand-off. Authenticates with its own `api-key` header, not Bearer.
- **Cloudflare Email** returns **per-recipient delivery status
  synchronously**: a permanent bounce is known at hand-off, hours before a
  callback would arrive — and Cloudflare sends no per-message callback at
  all. It returns **no message id**, and the adapter reports none rather than
  inventing one; a synthetic id in the attempt trail is a value no callback
  could ever join to.

**SMTP2GO / ZeptoMail: evaluated, skipped.** Neither offers anything the
generic SMTP relay does not already provide for a gateway of this shape, and
ADR-48 says a native adapter must earn its keep.

**Webhook security audit.** Only Resend publishes a cryptographic payload
signature (Standard Webhooks / Svix), and it is fully verified. Postmark and
Brevo publish none — confirmed against their live documentation — so their
adapters implement exactly what the providers do offer (mandatory endpoint
basic auth plus an optional source-IP allowlist) and **refuse a
`signing_secret` at startup**, because a verification an operator believes in
but nobody performs is worse than no verification. No signature protocol was
invented. No Brevo IP preset ships: its ranges live in a help-centre article
Posthorn cannot re-verify at build time, so the operator copies the current
list into `allowed_ips` themselves.

**RemoteQuota — final decision.** Never in the send hot path. Local usage is
authoritative for blocking; a remote reading is advisory and can only ever
RAISE the local counter, never lower it. Lowering on a lagging read would
hand back allowance already spent, which is the exact failure quota exists to
prevent. No vendor usage adapter ships, because none of the providers'
usage APIs were read carefully enough to report confident numbers into a
budget — the reference HTTP fetcher is generic and clearly labelled.

## 3. Security

Every item below has automated coverage; the live checks were additionally
run against a real running gateway.

| Area | Result |
|---|---|
| Secret scan (source, logs, metrics, all 15 SQLite tables, error bodies) | **clean** — 0 hits with sentinel credentials in every slot |
| Dependency vulnerabilities (`govulncheck`) | **no vulnerabilities found** |
| Go static analysis (`go vet ./...`) | **clean** |
| Race detector (`go test -race ./...`) | **clean**, 25 packages |
| HTTP security headers (admin) | `no-store`, `DENY`, `nosniff`, `no-referrer`, `default-src 'none'` |
| Path traversal | no filesystem surface; `/admin/../etc/passwd` → 301 → 404 |
| SQL injection | every filter parameterised; injection strings return empty sets, tables intact |
| Header injection (HTTP + email) | full CRLF battery per transport, incl. both new adapters |
| Open relay | dedicated suite; **two gaps found and closed** (below) |
| SMTP auth bypass | AUTH-before-MAIL, wrong-password, brute-force budget |
| Project isolation | structural via `Scope`; verified live across two projects |
| Admin isolation | project key rejected by admin API and vice versa; startup refuses a shared credential |
| CSRF | session ops require a token; verified live (403 without, provider unchanged) |
| XSS | server-rendered, contextual escaping, no script tag, CSP `default-src 'none'` |
| **SSRF** | parse-time **and connect-time**; DNS-rebinding and redirect hops covered |

**SSRF (ADR-49), the one called out for special attention.** Four
operator-supplied destinations — endpoint `webhook_url`, project
`webhook_url`, the remote quota URL, and the webhook transport — are checked
twice. Parse time catches the obvious cases with a legible error. **Connect
time is the boundary that holds**: `netguard.Policy.Control` runs on the
address the resolver actually returned, so a public-looking hostname that
resolves to `127.0.0.1` is refused, and every redirect hop is re-checked.
Blocked by default: loopback, private ranges, CGNAT, unspecified, multicast,
broadcast, and link-local. `[security] allow_private_webhook_targets` is the
documented opt-in for the ordinary self-hosted case where the receiver is the
operator's own app on `127.0.0.1` — and it **never** unblocks link-local,
because no webhook receiver lives on 169.254.0.0/16 and every cloud metadata
service does.

**Open relay — two real gaps found by writing the tests:**

1. `smtp.New()` would construct a listener with **no sender allowlist**. The
   config layer already refused it, so this was defense-in-depth rather than
   a live hole — but the constructor is where an open relay happens by
   omission, so it refuses now too.
2. `auth_required = "none"` together with `allowed_senders = ["*"]` was
   **accepted**. Each half is legitimate alone; together they are a mail
   server that accepts mail from anyone for anyone. Refused at parse time,
   with both halves still permitted separately.

An empty allowlist is pinned as failing **closed** — the opposite reading of
"no allowlist" is exactly how open relays happen.

**Secrets.** No API key was written into source, a test fixture, a log, a
metric label, a database column, or an error body. `.gitignore` covers
`.env*`, `*.secret`, `*.pem`, `*.key`, `credentials.toml`, `*.local.toml` and
`*.db*`; verified with `git check-ignore`, and no tracked file matches a
credential shape. `POSTHORN_ADMIN_TOKEN` is environment-only — config
**cannot** set it, so it cannot leak with a config file.

## 4. Production readiness

- **`/healthz` = alive; `/readyz` = able to serve** (ADR-55), wired to
  different signals on purpose. Readiness covers storage writable, an ingress
  configured, and workers started — that last one closes a real gap, since
  between the listener coming up and the queue drainer starting Posthorn
  would accept work nothing was draining. **A provider being down does not
  make Posthorn unready**: that is what the retry queue, breaker and failover
  absorb, and going unready would turn queued mail into refused mail.
- **Migration fails closed.** A database written by a newer Posthorn refuses
  to open. Migrations run forward from every prior version with data intact,
  are idempotent across restarts, and a corrupt file stops startup.
  *That test found a real gap:* `Open` proved a database READABLE, not
  writable — an already-current database runs no migration, so a read-only
  mount or full disk would open cleanly and fail on the first submission.
  Open now performs a canary write and refuses to return a store it cannot
  write to.
- **Container healthcheck now probes the running process.** It previously
  re-validated the config file, which passes happily while the listener is
  dead — the one failure a healthcheck exists to catch. `posthorn probe`
  ships as a subcommand because the image is distroless.
- **Compose deployment final:** loopback-bound port, `read_only` root,
  `no-new-privileges`, `cap_drop: ALL`, tmpfs for scratch, `mem_limit 256m`,
  `pids_limit 128`, bounded log rotation, bounded database size so Posthorn
  cannot fill the volume its own queue lives on, `temp_store = MEMORY` so a
  large query does not need a writable `/tmp`.
- **Provider config reload: RESTART** (ADR-57). Hot reload was evaluated and
  declined — its failure modes are all silent (a send routed to a replaced
  transport, a breaker whose history is discarded, a quota counter reset by
  an edit), and the alternative costs one sub-second restart behind a durable
  queue. The incident path is the admin kill switch, which is immediate.
- **`examples/production.toml`** with every secret as an env placeholder,
  validated end to end.

## 5. Admin

- **Separate credential.** `POSTHORN_ADMIN_TOKEN`, minimum 24 characters,
  environment-only. Startup **refuses** when it collides with any project API
  key or SMTP password — sharing one would let a tenant's application key
  read every tenant's delivery history. Not configured means the routes are
  **not mounted**; "no token" never degrades into "no authentication".
- **Sessions.** The login form exchanges the token for a cookie: HttpOnly,
  `SameSite=Strict`, `__Host-` prefixed and Secure over TLS, 8-hour idle
  life. The token never reaches the page and is never in `localStorage`. The
  session id is not derived from the token. Login failures are throttled per
  source, and the **correct** token is refused while locked out — otherwise
  the limit only slows down the last guess.
- **What it shows.** Dashboard, providers (circuit, quota, capability row),
  projects, messages, attempts, events, retry queue, dead letters,
  suppressions, audit log — as HTML and as JSON.
- **What it never shows.** Message bodies: nowhere, in any view. Full
  recipients: masked to `u***@example.com`, because an admin surface listing
  every recipient is a harvestable directory of every user of every tenant.
  Credentials: not masked on the way out but **absent**, because Posthorn
  does not store them — only digests. The projects page renders a
  *fingerprint* of the digest, enough to see that a key rotated.
- **Five audited operations:** disable/enable a provider, reset a breaker,
  suspend/restore a project, retry a dead letter, remove a suppression.
- **Overrides can only SUBTRACT** (ADR-51). Clearing one restores what the
  config says; it cannot summon a provider the config omits or enable a
  project the config disabled. Config remains the source of truth, and this
  remains a kill switch. Verified live: disable → the route skips it and mail
  **queues rather than dropping**; restart → still disabled.
- **The UI has no JavaScript** and loads no external asset. There is nothing
  to inject into, and the HttpOnly cookie means something because the page
  never needs to read it.
- **Audit log** (ADR-53): written **before** each action takes effect,
  aborting the action if the row cannot be written — a crash between the two
  leaves a recorded action that did not happen, which is checkable; the
  reverse leaves an untraceable change, which is not. Exempt from retention
  pruning. No column for a secret. The unsuppress entry records the **masked**
  address.
- **Key rotation** (ADR-52): a config overlap, no downtime, no endpoint that
  can mint a key. Verified live — both keys authenticating simultaneously,
  the admin surface showing "2 keys live", and the startup audit entry
  written from a digest-of-digests comparison.

## 6. Storage

- SQLite, WAL, `busy_timeout=5000`, `foreign_keys=ON`, `synchronous=FULL`,
  `temp_store=MEMORY`, `max_page_count` derived from `max_size`.
- Single connection: serialized access, single-writer by construction.
- Schema `user_version` **6**. This round added `audit_log`,
  `admin_overrides`, `project_key_state`.
- **Load regression (this round, after every addition):**

  | concurrency | requests | elapsed | rps | p50 | p99 | outcome |
  |---|---|---|---|---|---|---|
  | 100 | 100 | 1.09s | 92 | 47 ms | 1079 ms | 100 × 200 |
  | 500 | 500 | 1.37s | 366 | 98 ms | 1067 ms | 500 × 200 |
  | 1000 | 1000 | 1.80s | 555 | 232 ms | 1122 ms | 1000 × 200 |

  1,600 submissions, **0 failures, 0 SQLITE_BUSY, 0 error-level log lines**.
  Process footprint at 1000 concurrency: **48 MB RSS, 13 threads**. Project
  usage recorded exactly 1600/1600. The query API paged all 1,600 rows across
  8 pages in 0.07s with no duplicates.
- **`kill -9` recovery, re-verified this round:** killed mid-flight under
  load, 31 submissions were left `sending`; on restart all 31 became `queued`
  and drained to `sent`, with `integrity_check ok` throughout. That window is
  the documented at-least-once duplicate risk (ADR-46).

## 7. Backup and restore

- **`VACUUM INTO`, never a file copy** (ADR-56). The naive backup is wrong for
  a WAL database twice over: recent writes live in the `-wal`, and there is no
  instant at which `cp` sees a consistent set of all three files.
- Runs on a **live** database — no downtime to take a backup, and no need to
  know WAL exists to take a correct one.
- Verified immediately after writing, so a bad backup surfaces while someone
  is watching. Refuses to overwrite an existing file.
- **Verified against real data this round:** a 1,821-submission database
  backed up while quiesced and compared row-by-row — **14/14 tables
  identical**, `integrity_check ok` — then restored and served immediately.
- **Restore is offline and says so.** *A defect found by running it against a
  real database:* the in-use check was a `-shm` file heuristic, and SQLite can
  leave a `-shm` behind after a clean shutdown — so a stopped database
  reported as "in use" and refused the restore, at exactly the moment an
  operator needs one. It now **takes the write lock**, which is the question
  that actually matters. Verified in both directions against a live gateway.
- The superseded database is renamed aside, not deleted; stale `-wal`/`-shm`
  are cleared so they cannot be applied on top of the restored file.

## 8. API

**Project-scoped read API** (ADR-50): `GET /v1/messages`, `/v1/messages/{id}`,
`/{id}/attempts`, `/{id}/events`, `/v1/usage`.

- **Isolation is structural.** Every storage query takes a `Scope` with
  unexported fields; the only way to read across projects is to call
  `AdminScope()` by name, so a missed filter is a compile error or a
  greppable call site rather than a silent leak.
- The scope comes from the **authenticated credential only**. A `project`
  query parameter is not read — a client-supplied tenant name is not a fact.
  Verified live: `?project=globex` with acme's key returns acme's rows.
- A foreign message returns **404 with the same body** as a missing one, so
  the endpoint is not an oracle for guessing other tenants' message ids.
- Sub-resources check message visibility **first**, because `message_attempts`
  has no project column and joining is exactly the filter that gets forgotten.
- **No message content** — `body_text` and `body_html` appear in no SELECT in
  this surface, so there is nothing to mask incorrectly. No body or subject
  search, deliberately.
- Pagination is `(created_at, id)` cursor-based, so rows sharing a second are
  neither repeated nor skipped; cursors are opaque and validated; `limit` is
  clamped to 200.
- Read-only by **routing table** — every route is registered as a GET
  pattern, so a POST is a 405 from the mux.

## 9. Metrics

Final cardinality audit passed (NFR24, ADR in `metrics/cardinality_test.go`).
Every exported `Recorder` method is called reflectively with a sentinel, and
the emitted label vocabulary must be exactly:

`endpoint`, `transport`, `provider`, `router`, `project`, `window`, `status`,
`outcome`, `result`, `reason`, `kind`, `check`, `error_class`, `state`,
`event`, `type`, `le`.

**Forbidden and structurally impossible:** message ids, submission ids,
recipients, senders, subjects, bodies, provider error strings, idempotency
keys, client IPs, URLs. The Recorder API does not accept request-side values,
so there is no parameter for one to travel through. Metric **names** are
audited too, and nothing address-shaped reaches the exposition. Documented at
`/reference/metrics/` with the full metric list and the policy.

- Every historical scenario re-run: header injection across all transports,

  verification and disorder, crash recovery, disk-full degradation, provider
  failure matrix (401/403 confirmed **not** failing over), suppression

- Hermetic provider e2e battery extended to both new adapters, including the

- Live checks against a running gateway this round: auth separation, project

## 11. Load

See §6. Summary: 555 rps at 1000-concurrency, p99 ~1.1s, 48 MB RSS, 13
threads, zero SQLite contention, zero errors, exact quota accounting.

The p99 sits just above 1s at every concurrency level, which is the inline
retry backoff on the first attempt rather than saturation — p50 rises from
47 ms to 232 ms across a 10× concurrency increase, so the system is not near
a knee.

## 12. Accepted limitations

Stated rather than implied:

1. **Delivery is AT-LEAST-ONCE** (ADR-46). No configuration makes it
   exactly-once. A provider can accept a message and have its response lost;
   Posthorn cannot distinguish that from a failure and prefers a duplicate to
   a loss. The caller-side convention that neutralises it — keep the same
   business token across retries of one logical message — is documented.
2. **Webhook verification is impossible for Postmark and Brevo**, because
   they publish no payload signature. Anyone holding the endpoint's
   basic-auth credential can forge their events; the IP allowlist narrows the
   path without authenticating the payload. Stated in the matrix as
   `unsupported`, not as a gap.
3. **Cloudflare Email returns no message id**, so its sends cannot be
   correlated to a provider dashboard entry by id, and it has no delivery
   webhook at all.
4. **Provider config changes require a restart** (ADR-57).
5. **Single instance.** No HA, no horizontal scaling, no multi-region. A
   restart is a brief outage of the HTTP ingress; queued mail survives it.
6. **Project daily/monthly limits** are enforced; provider quota is enforced
   locally. Remote provider usage is advisory only and no vendor adapter
   ships.
7. **The admin surface has one credential and no roles.** Complex RBAC is an
   explicit non-goal.
8. **`allowed_senders = ["*"]` behind authentication is permitted** — an
   operator decision, documented, with the recipient allowlist as the
   remaining control. Only the combination with `auth_required = "none"` is
   refused.

## 13. Remaining

Nothing in the v1.0 scope is unimplemented. What remains is external:

1. **Real-credential E2E** (§10). This is the only gate blocking a `v1.0.0`
   tag.
2. **Mailbox rendering checks** against Gmail / Outlook / iCloud, which need
   both credentials and real mailboxes.
3. Operational debt inherited from earlier releases: Mailgun, SES and the
   outbound-SMTP relay still have no recorded live validation.

## Verdict

# PRODUCTION READY — with one gate open

Every gate that can be closed without credentials is closed: architecture,
provider correctness, isolation, secret handling, SSRF, open relay, CSRF,
XSS, injection, cardinality, migration, backup/restore, crash recovery, load,
and the full regression suite under the race detector. Four real defects were
found and fixed during this round rather than being written around — the
`smtp.New` allowlist bypass, the `auth_required=none` + wildcard combination,
the write-canary gap at Open, and the restore in-use false positive.

The **only** blocking item is real-credential E2E, which is
`BLOCKED_BY_CREDENTIALS` and is not marked passed.

**Therefore, per the release gate: tag `v1.0.0-rc.1`, not `v1.0.0`.**

Promote to `v1.0.0` after running, with real credentials:

```bash
export RESEND_API_KEY=...            # real send + real webhook signature
export POSTHORN_TEST_TO=...          # a mailbox you own
export SMTP_HOST=... SMTP_USER=... SMTP_PASSWORD=...
go test -tags integration -run TestLive ./providertest/
```

and confirming: a real Resend delivery, a real verified Resend webhook, a
real SMTP relay delivery, a real failover between two live providers, and
mailbox rendering in at least Gmail and Outlook.
